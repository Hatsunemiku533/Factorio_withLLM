# Factorio × LLM 共同工厂：实现调查

调查日期：2026-10-02。范围：只读核对官方文档与 FLE 源码，并检查本机是否已有 Docker / Factorio / Python。没有安装游戏，没有拉镜像，没有启动服务器。

> 阅读边界（2026-10-03 整理）：上述范围及第 1–15 节是最初的只读调查，不是当前状态。第 16–24 节记录后续实施与实测；现行路线是自建 `save-safe-bridge 0.6.0`（schema 6）+ 受限 MCP，不使用 FLE 运行时。后台循环只是早期提案，尚未实施。当前目录、连接、部署与权限以 `README.md`、`AGENTS.md` 和实际配置为准。

目标按你的原话收束：**一个保留存档的小工厂，你能进来巡视和帮忙，AI 从简单生产任务开始。**

结论先说：这条路线成立，也适合「后台挂着、你偶尔进来看、有时亲手改一改」。现成的 FLE 不能直接当这个产品用。必须拆成三层——游戏世界、不会清场的适配器、独立的 LLM 循环——并用 Factorio 原生存档当唯一世界真源。

## 1. 目标与非目标

要做的是同一个长期世界：

1. 工厂在你不看的时候继续运转（服务器 `auto_pause: false`）。
2. 你用正常 Factorio 窗口连进去，缩放地图、走路、摆放、拆改。
3. AI 用程序接口建造，不必假装每帧拖鼠标。
4. 重启电脑或重启容器后，还能回到同一张图。
5. AI 跨会话留下技能和失败经验，不只留下存档。

明确不做：

- 不追求发射火箭或 megabase。
- 不把 FLE 的 lab-play 配额评测当成玩法。
- 不把当前这场 OpenCode 聊天当成后台工人。回复结束，这条会话就停。
- 不把研究用快照（`GameState`、MCP undo）当成「保存游戏」。

## 2. 原始推荐架构（历史，FLE 适配路线已放弃）

把它想成一座一直开着的工厂，外加一个会用工具的同事，而不是「启动一次评测、结束时复原场地」。

```
你的 Factorio 窗口  ──UDP 34197──►  Docker 里的 Factorio 服务器
                                         │
                                         │ RCON 本机 TCP
                                         ▼
                               适配器（改过的 FLE 连接）
                                         │
                                         ▼
                          OpenCode 会话 / 定时 `opencode run`
                                         │
                                         ▼
                          本目录 memory/（技能、事件、当前任务）
```

三层职责分开：

| 层 | 用什么 | 负责什么 | 不要让它负责什么 |
|---|---|---|---|
| 世界 | Factorio 专用服务器 + 原生 `.zip` | 模拟、联机、自动保存、你看见的画面 | 模型决策 |
| 适配器 | FLE 的 RCON / `eval` / 放置工具，去掉清场初始化 | 让 AI 查询库存、放机器、接传送带 | 重置地图、回滚你的改动 |
| 循环 | 本项目的会话规则 + OpenCode | 读状态、做下一步、写经验、遵守停机与用量 | 直接 `fle inspect-eval` 或默认 MCP lifespan |

这不是「装一个插件就完成」。FLE 已经把最难的游戏 API 写好了；我们要补的是**共同世界纪律**和**持续玩耍循环**。

## 3. 游戏本体：开源吗、怎么联机、怎么存

Factorio **不是开源游戏**。EULA 写明源码与美术版权归 Wube，许可是买断后的个人非商用使用。〔官方〕

要看画面、要走进去帮忙，需要一份**完整客户端**。官方有免费 Demo，只适合判断喜不喜欢，不能默认拿 Demo 去连 FLE 服务器。Linux **无画面 headless 包免费**，EULA 甚至允许用它开商用服务器；那是服务器，不是你的游戏窗口。〔官方〕

联机要点〔官方 wiki Multiplayer〕：

- 协议只有 **UDP**，默认端口 **34197**。
- **所有实例的游戏版本和 mods 必须完全一致**，连上时会比对 checksum。
- 专用服务器启动必须先有存档：`--create` 生成，`--start-server save.zip` 载入。
- headless 服务器在游戏里**没有角色**。要巡视或动手，必须用客户端连进去。
- `server-settings.json` 里 `visibility.public / lan` 控制是否出现在公共列表或局域网；`auto_pause` 控制没人在线时要不要暂停。
- 管理员命令 `/server-save` 可立刻存盘。wiki 写 headless 退出时会保存，但「用哪种方式杀进程才算退出」〔待测〕。

雷达决定你在地图上能看见多远〔官方 wiki Radar〕：玩家自己揭示约 5×5 chunk；雷达持续视野约 7×7 chunk；更远处只有「上次扫到的最后已知状态」。AI 在远处搭的东西，你不一定在地图上实时看到细节，走进去或补雷达才能看清。这不影响「能巡视」，只影响「不走路就看全图」。

Space Age 是另购 DLC。第一期只做本体即可。FLE 启动命令会删掉容器里的 `elevated-rails` / `quality` / `space-age` 数据，方便没买 DLC 的客户端同步 mods。〔源码〕

当前官网稳定版是 **2.0.77**（下载页，2026-10-02）。Linux headless 2.0.77 约 54.6 MiB；Windows Demo zip 约 1.38 GiB。完整付费客户端体积未确认。价格是区域动态，这次没读到金额，不编。〔官方〕

## 4. FLE 能提供什么

仓库：https://github.com/JackHopkins/factorio-learning-environment  
钉死的代码点：`e2a829d22a635a9a111d21bf5523e09e903ae145`（Release 0.4.8 说明，2026-09-06）。  
PyPI / `pyproject.toml` 版本：`0.4.8`。  
GitHub Release 只打到 **v0.4.3**（2026-04-06）。0.4.4–0.4.8 没有 tag。〔源码〕

它对这个项目真正有用的部分：

1. **把 Factorio 跑在 Docker 里**，镜像 `factoriotools/factorio:2.0.73`（第三方镜像，不是 Wube 官方）。单实例默认宿主端口：游戏 `34197/udp`，RCON `27000/tcp`，RCON 密码 `factorio`。
2. **Python API**：`FactorioInstance.eval(code)` 在游戏里执行一段 Python 风格的放置/连接代码；工具包括 `place_entity`、`connect_entities`、`move_to`、`craft_item`、`get_entities` 等。
3. **MCP 包装**：`python -m fle.env.protocols._mcp`，可被 OpenCode 当本地 MCP 用。但见下一节，默认生命周期不能用。
4. 可选渲染、Gym、inspect-eval。那些是研究评测，不是共同工厂。

AI 的默认操作模式是 `fast=True`：移动用 `teleport`，手搓用直接扣料插入。看起来不像真人走路，但建造结果是真的。若以后要更像玩家，可改 `fast=False`，代价是更慢。〔源码〕

`get_entities` 按玩家阵营、以角色或坐标为中心、带半径，不是无限全图作弊视野。半径开很大时近似大范围读取。〔源码〕

## 5. 为什么不能原样接入（这是核心）

下面几条叠在一起，会直接破坏「保留存档 + 你进来帮忙」。

### 5.1 只要按常规方式连接，就会清场

`FactorioInstance.__init__` 会调用 `initialise()`。`initialise()` 会：

1. 调用 `_create_agent_characters`。对应 Lua **先销毁地表上所有 `type="character"` 实体**，再在 `{0, (i-1)*2}` 重建 AI 角色。你的角色也是 `character`，会被删掉。
2. 默认 `peaceful=True`，清敌人。
3. 在原点周围强制生成 25 chunk。
4. 调用 `_reset(..., clear_entities=True)`。

`clear_entities` 不是「清 AI 脚下一点点」。源码注释写明：**整个地表、该阵营的生产/物流/电力/箱子等实体全部 destroy**，连掉在地上的物品也清。你刚摆的炉子、传送带都在这个列表里。〔源码 `fle/env/tools/admin/clear_entities/server.lua`〕

MCP 的 `create_factorio_instance()` 构造 `FactorioInstance(...)` 时走同一条路，并且 `fast=True`、还会 `set_speed(10)`。〔源码 `fle/env/protocols/_mcp/state.py`〕

### 5.2 会话结束再 reset 一次

MCP `shutdown_session()`：

```python
state.active_server.reset()
state.active_server = None
```

无参 `reset()` 会 `game.reset_game_state()`、重生资源、清实体、重置库存、把科技树 `force.reset()`。这是全世界级操作。〔源码 `fle/env/protocols/_mcp/init.py`、`tools/admin/reset/server.lua`〕

`FactorioMCPState.__init__` 在导入时还会 `gym.make(...).reset()`，可能顺手拉起/重置一个评测环境。〔源码〕

### 5.3 默认不是「继续上一张图」

有两套 compose 生成器：

| 入口 | 谁在用 | 默认启动 | 存档卷 |
|---|---|---|---|
| `fle cluster` → `run-envs.sh` | CLI | `--start-server-load-scenario default_lab_scenario` | 只有 `-sv save.zip` 才挂 `.fle/saves` |
| Python `ClusterManager` | inspect-eval 自动拉起 | 同样默认场景 | 只有 `save_file` 非空才挂 `%LOCALAPPDATA%\fle\saves` |

默认每次都是**新场景**，不是加载上次的 zip。即便容器里写出了 autosave，下次 `start` 也不会自动续上。〔源码〕

Windows 上 `fle cluster` 直接执行 `.sh`，很大概率失败；Git Bash 存在（`C:\Program Files\Git\git-bash.exe`），应用它来跑脚本，或改走 Python `ClusterManager`。〔本机 + 源码〕

### 5.4 默认服务器配置对「共同工厂」不友好

FLE 的 `server-settings.json`〔源码〕：

- `visibility.public: false`，`lan: true`：不会上公共列表，局域网可见。方向对。
- `auto_pause: false`：没人在线也继续跑。符合后台工厂。
- `require_user_verification: false`，`game_password: ""`。
- `autosave_interval: 10`，但 **`autosave_slots: 0`**。官方示例一般是 5 个槽。0 是否等于「不留自动存档」〔待测〕，实施时应改成明确的正数，例如 5。
- 启动参数带 `--use-server-whitelist`，配置目录里**没有** `server-whitelist.json` / `server-banlist.json`。白名单若按空文件生效，结果可能是谁都进不去。〔待测，优先修〕
- 文件里有一个 Factorio.com `token` 字段。那是别人仓库里的凭据痕迹，**不要复制进本项目**。本地只留空，或填你自己的。

管理员列表只有 `["client_master"]`。你进游戏后的用户名若不在名单里，就没有 `/server-save` 等管理命令。需要把你的游戏用户名加进去。〔源码〕

### 5.5 研究快照不是完整存档

`GameState` 只序列化一定范围内、玩家阵营的实体、库存、科技和命名空间变量。不含完整地形、电路网络细节、列车调度、敌对实体、原生 `level.dat`。MCP 的 commit/undo 先 `reset` 再把这份有损快照灌回去，会抹掉快照没覆盖的东西，包括你在范围外的建筑。〔源码〕

**世界真源只能是 Factorio 的 `.zip`。** 快照最多当 AI 的实验草稿，而且不要在共同世界上对它按 undo。

## 6. 「你进来看看、帮忙点一点」具体怎么做

游戏层是支持的。专用服务器 + 客户端连 `127.0.0.1:34197`（或局域网广播）就是标准联机。你是普通 `LuaPlayer`，有自己的角色，和 AI 共用 `force "player"`。因此：

- 能看：打开地图、缩放、走路、看传送带和机器。远处实时细节受雷达限制。
- 能改：摆放、拆除、改配方、补煤。AI 的 `get_entities(force=player)` 看得到你建的东西。
- 也会互相干扰：你们抢同一片矿、拆对方的带子、AI 若再跑 `clear_entities` 会把你的工厂一起删掉。

所以适配器必须做到：

1. **先做 attach-only 探针，再谈 adapter。** “脚本已加载后只建立 RCON、跳过 `initialise()` 就能连接已有世界”仍是待验证假设。探针只能加载必要能力并做只读查询，全程不能 reset；成功后才继续 adapter。
2. **创建 AI 角色时，只补缺失的 agent character，禁止 `find_entities_filtered{type="character"}` 后全部 destroy。**
3. **禁止对共享世界调用 reset / clear_entities / MCP undo。**
4. **划区（第一期可用约定，不必先做围栏 mod）**：例如 AI 只在坐标某一侧建造；你在聊天或 `memory/current.md` 里写「原点西侧是我的，别拆」。
5. 人类进游戏时，若 AI 正在执行长代码，适配器应能失败重试，而不是回滚世界。

这些改动在 FLE 源码里都有明确挂钩点，但官方没有「共同世界模式」开关。要自己包一层，不要 fork 整份评测栈。〔推断，实施时验证〕

## 7. 持久存档怎么做

正确顺序：

1. 用与客户端相同版本的服务器 **创建一次** 存档（`--create` 或在客户端里新游戏后另存，再拷进服务器 `saves/`）。
2. 以后只 `--start-server 那个.zip`，或 `--start-server-load-latest`。
3. `autosave_interval` 设 5–10 分钟，`autosave_slots` 设正数。
4. 停服务前尽量发 `/server-save`，再正常 stop。
5. 把 `saves/` 放在本项目 `world/`，Docker 只绑定这一目录。不要依赖 FLE 两套默认路径（仓库旁 `.fle/saves` vs `%LOCALAPPDATA%\fle\saves`）。

`docker compose down` 默认不删 bind mount 里的 zip。真正的风险是**下次用场景启动覆盖了世界**，不是容器删除。〔官方 + 源码〕

第一期建议：和平、关闭或减弱虫族、小地图。后台工厂被袭击会在你不在时毁掉进展；这是玩法选择，不是技术限制。FLE 默认 `peaceful` 清敌人，方向符合「小工厂」。

## 8. LLM 循环：OpenCode 怎么接

OpenCode 1.18.18 已在本机。它适合**你看着的时候**指挥 AI，也适合做成「工厂同事」agent。它**不能**在这条聊天回复结束后自己继续玩。〔本机 + OpenCode 文档〕

可用的官方能力〔https://opencode.ai/docs/cli/ 、 /docs/mcp-servers/ 、 /docs/server/〕：

- 项目内 `AGENTS.md`、专用 agent：限制工具、固定「不许 reset」。
- 本地 MCP：`type: "local"`，`command` 启动适配器。
- `opencode run --continue --session <id> "下一步：检查铁板产量"`：给外部定时器调用。
- `opencode serve`：常驻后端，避免每次冷启动 MCP。

推荐演进：

1. **阶段 3**：你在本目录开一个 OpenCode 会话，手动说「去把矿机摆上」。你能在游戏窗口里看见结果。
2. **阶段 4**：一个很小的调度（Windows 计划任务或脚本）每隔 N 分钟调用一次 `opencode run --continue`，并写入停机条件（产量达标、连续失败、今日 token 上限）。
3. 不要用 `fle inspect-eval` 当玩耍循环。它会按评测任务 reset、限步数、默认模型 `openai/gpt-4o-mini`，和共同世界冲突。

费用：用 OpenCode 当前已登录的模型，走你现有通道；用 FLE 自带评测脚本，则要它自己的 `.env` API key，不包含在 OpenCode 订阅里。后台挂着会持续耗 token，必须有上限。具体单价以你控制台为准，这里不编数字。

上下文：FLE 工具说明本身就很长。共同工厂 agent 应只开游戏 MCP，关掉无关 MCP，任务要短（「先做出稳定铁板」而不是「自己规划文明」）。

## 9. 经验怎么积累

游戏存档 ≠ AI 记忆。模型权重不会因为多玩几天而更新。要留下的是文件。

建议以后在本目录放：

| 文件 | 写什么 | 不写什么 |
|---|---|---|
| `world/*.zip` | 唯一世界 | AI 感想 |
| `memory/current.md` | 当前目标、禁区、你刚说的话 | 长篇复盘 |
| `memory/skills.md` | 验证过的做法：条件、步骤、失败信号 | 没跑过的设想 |
| `memory/log.md` | 按日一行：做了什么、产量、翻车 | 每步思维链 |
| `traces/` | 可选的原始对话，gitignore | 当记忆用 |

技能条目要短，例如：「烧铁：矿机朝炉子，煤要单独供，缺煤时炉子停转」。失败也留下：「把矿直接铺进组装机无效，必须先炼板」。

检验进步：同一张图上，铁板从手工 → 自动供矿 → 带子连上。不要用没玩过的随机种子当第一期指标。

## 11. 分阶段实施

原则：**先证明世界还在，再让 AI 碰它。**

### 阶段 0 — 前置（你来确认）

- 购买并安装 Factorio 本体，记下确切版本号。
- 启动 Docker Desktop，确认 `docker info` 能连上引擎。
- 决定服务器版本：跟着客户端，或把客户端回退到 `2.0.73` 以匹配 FLE 默认镜像。
- 确认模型通道与每日上限。

安装位置：游戏按官方/Steam 默认即可。项目代码、存档、记忆放本目录。FLE Python 包建议新建独立 conda 环境，不要塞进 `floris_env` 或 `tools_for_ai`。镜像会占磁盘，具体体积〔待测〕，预计数百 MB 到数 GB 量级。

### 阶段 1 — 只有世界，没有 AI

验收：你能进服务器、摆一台炉子、停容器、再启动、炉子还在。

要做：固定版本镜像；自己的 `server-settings`（关 public、开 lan、`auto_pause false`、autosave 槽位 >0、空白或允许你进的白名单、空 token、管理员含你的用户名）；RCON 只绑 127.0.0.1；存档在 `world/`。

这一阶段失败，后面全部白做。

### 阶段 2 — 不会清场的适配器

验收：RCON 能查实体；用 API 放一台采矿机；你的角色和炉子还在；断开适配器再连，世界仍在。

要做：封装 `FactorioInstance`，跳过破坏性 `initialise`；创建 AI 角色改为「没有才建」；MCP 若用，去掉 `shutdown_session` 里的 `reset`，去掉导入时的 `gym.reset`。

### 阶段 3 — AI 做第一件生产任务

任务建议：**稳定的铁板**（矿机 + 熔炉 + 煤）。肉眼能看懂，失败也容易救。

验收：你在窗口里看见自动产出铁板；过程写入 `memory/log.md`；至少一条技能写进 `memory/skills.md`。

### 阶段 4 — 你帮忙，它接着干

验收：你改了传送带或补了煤，AI 下一轮读到新布局，继续补全而不是按旧坐标硬盖，更不会 reset。

### 阶段 5 — 轻度后台

验收：你离开后工厂继续转；调度按间隔叫一次模型；达到停机条件会停；token 有上限。

不要在阶段 1 没过之前做阶段 5。

## 12. 最小探针（实施时按顺序跑，现在不要跑）

1. **版本一致**：客户端关于页版本 = 容器 `factorio --version`。
2. **Docker 引擎**：`docker info` 成功。
3. **进得去**：客户端连 `127.0.0.1:34197`，能移动、能建造。若进不去，先查白名单和版本。
4. **续得上**：建造标记物 → `/server-save` 或等 autosave → `compose down` → 用同一 zip 启动 → 标记物仍在。
5. **RCON 只读**：本机连 27000，查实体，不调用 reset。
6. **适配器不杀角色**：你站在游戏里，适配器连接后角色还在。
7. **API 放置**：适配器放一台矿机，你能看见。
8. **断开不清场**：停适配器，工厂不变。
9. **人类改动可见**：你拆一根带子，AI 下一轮观察里没有那根带子。
10. **任务闭环**：铁板开始自动产出。

1–4 不需要模型。5–8 不需要「聪明」的模型，任意能调工具的会话即可。

## 13. 风险与成本

| 风险 | 为什么重要 | 怎么处理 |
|---|---|---|
| 客户端与服务器版本不同 | 对不上就无法联机 | 第一阶段主动统一为 2.0.73；这不是 FLE 的版本上限 |
| 默认 MCP / `FactorioInstance` 清场 | 会删你的工厂和角色 | 阶段 2 必须先改，禁止直连官方 MCP |
| `autosave_slots: 0`、场景启动 | 看起来在跑，重启却回到空白 | 自己的 compose 与 settings |
| 白名单缺文件 | 你根本进不去 | 阶段 1 先测加入 |
| Windows 跑 `.sh` | `fle cluster` 可能直接失败 | Git Bash 或 Python ClusterManager |
| Docker 未启动 | 现在就是这个状态 | 开 Docker Desktop |
| 还没买游戏 | 没有观看与共建窗口 | 先 Demo 再决定买 |
| 后台 token | 挂着就会烧 | 日上限、失败熔断、任务要短 |
| AI 建造质量 | FLE 公开结果显示模型常摆错、读错库存 | 第一期只要求「能看见它试」，不要求名厂 |
| 第三方 Docker 镜像 | 不是 Wube 官方 | 只用本机端口，不公开 |
| 把评测 undo 当后悔药 | 会抹掉你的建筑 | 规则写进本目录 AGENTS.md |

工具投入（对应全局档案「超过约 30 分钟要先问」）：阶段 1 起就会超过。一个月里你真会打开几次、现在有多想看它玩、Docker/游戏是否由你控制、愿意先花几小时，这些要你自己说。调查本身不安装。

## 18. 阶段 2B 实测（2026-10-03）

阶段 2B 已通过。它证明最小 save-safe bridge 可以安装在长期世界的测试副本上，并支持观察查询、保存、重启和人类客户端加入。

这里的“观察”不是零写入。`get_entities` 不修改实体、玩家、库存、速度或工厂布局，但它会把 `storage.save_safe_bridge.query_count` 加一。这个计数只属于 bridge 自己的诊断数据。

路线依据：

- FLE issue #381 报告 `storage` 中的 Lua function 无法序列化，导致持久服务器不能保存。
- FLE issue #417 进一步说明客户端加入会强制保存，因此这个问题也会阻断人类加入；运行时注入的事件处理器还会造成客户端与服务器不匹配。
- `bdambrosio/Cognitive_workbench` 使用 Factorio `2.0.73`，并把 FLE Lua 打包成普通 mod。该仓库为 MIT 许可证。本轮只采用它的架构原则，没有复制其完整 `fle-bridge`。
- 原则是：函数留在 mod 的普通 Lua 状态，`storage` 只保存可序列化数据，不动态注册事件处理器，也不创建 agent character。

实现与隔离：

- 新 mod 位于 `mods/save-safe-bridge/`，版本 `0.1.0`，只暴露 `status` 和 `get_entities`。
- `get_entities` 显式接收 surface、force、坐标和半径，最大半径为 32。它不调用 `ensure_valid_character`，也不会在缺少角色时创建角色。
- Python 探针 `adapter/bridge_probe.py` 仍只导入 `factorio_rcon.RCONClient`。它通过 `/sc` 调用 `remote.call("save_safe_bridge", ...)`。
- 实验没有使用正式 `world/shared-world.zip`。它被复制为 `world-test/bridge-test.zip`，由独立容器 `factorio-bridge-test` 加载。
- 测试服宿主端口是 `127.0.0.1:34297/udp` 与 `127.0.0.1:27115/tcp`。正式服继续占用原来的 `34197/27015`。
- 客户端使用 `%APPDATA%\Factorio\mods\save-safe-bridge_0.1.0.zip`，与服务器 mod 内容相同。

实测结果：

- 首次查询读到 `stone-furnace`，位置仍是 `(3, 4)`，`game.speed` 为 `1`，没有 character。
- `/server-save` 后测试存档从 947,866 字节增长到 950,074 字节。停止并重启后，bridge 的 `query_count` 从 1 增加到 2，证明 `storage` 中的数据被成功保存并恢复。
- 日志没有 `Cannot serialise lua functions`，也没有 event-handler mismatch。
- Windows 客户端加入 `127.0.0.1:34297` 后，日志出现 `[JOIN]`。玩家 `127.0.0.1` 的角色 `unit_number` 为 `1`，且是唯一 character。
- 人类在线时再次 `/server-save` 成功。保存后角色编号、石炉 `unit_number` 和实体组成都不变，`query_count` 继续增加到 4。
- 整个过程结束后，正式 `world/shared-world.zip` 仍是 947,866 字节，修改时间仍是 `2026-10-03T00:39:42.5954525+08:00`。

阶段 2B 没有实现放置、移动、AI character、FLE MCP 或后台模型循环。下一轮必须另行审查后才能扩大 bridge 能力。

## 19. 阶段 2C 实测（2026-10-03）

阶段 2C 已通过。测试世界里现在同时有人类角色和一个不会自主行动的蓝色 AI character，双方都能跨保存与重启保留。

- `save-safe-bridge` 升级到 `0.2.0`，新增 `ensure_agent_character` 与 `agent_status`。
- 已有且有效的 AI character 会被直接返回，不会重复创建。

- 持久标识同时使用 Factorio 可序列化的 LuaEntity 引用和纯数据 `unit_number`。调用时两者必须匹配；引用失效时直接报错，不允许偷偷再建一个。

## 20. 阶段 2D 实测（2026-10-03）

阶段 2D 的功能验收已通过，但移动表现不够平滑。

实现：

- `save-safe-bridge` 升级到 `0.3.0`，新增 `walk_to`、`movement_status`、`stop_agent`、`give_stone_furnace` 和 `place_stone_furnace`。
- 寻路使用 `LuaSurface.request_path`，角色碰撞盒和碰撞掩码取自 character prototype。路径结果只保存为坐标数据。
- 移动使用静态注册的 `on_tick` 持续设置 AI character 自己的 `walking_state`。代码没有 teleport，也没有改 `game.speed`。
- 放置前检查移动状态、建造距离、AI 自己的库存和目标碰撞。放置成功后从 AI 库存扣除一台石炉。
- 这里使用的是 `surface.create_entity` 加上述检查，因此应称为“模拟玩家建造语义”，不能称为调用了 `LuaPlayer` 的手动建造 API。

实测结果：

- 调试行走从 `(8, 0)` 到 `(14, 0)`，路径有 6 个点，最终停在 `(13.48, 0.21)`，速度保持 `1`。
- 用户在线时看到蓝色角色走向 `(20, 0)`。最终路径有 7 个点，停在 `(19.5, 0.21)`，角色编号仍是 `15`。
- 随后在 `(22, 0)` 放下新石炉，实体编号 `16`，AI 库存从 1 减到 0。
- 保存、停止和重启后，编号 `15` 的角色与编号 `16` 的新石炉都还在；旧石炉编号 `14` 仍位于 `(3, 4)`。
- 用户重新加入后，人类角色编号仍是 `1`。在线再次保存成功，日志没有函数序列化错误或事件处理器不匹配。
- 正式 `world/shared-world.zip` 仍是 947,866 字节，修改时间仍是 `2026-10-03T00:39:42.5954525+08:00`。

## 26. 阶段 4AB-R Gate A：所有权持久化（2026-10-03，通过）

根因：schema 7 使用 `owned_machines[unit_number] = true`。Factorio 序列化 mod `storage` 时不保留值为布尔 `true` 的表项，因此保存并重新加载后记录消失，`inspect_entity` 返回 `owned=false`。这不是 schema migration 主动清空，也不是 `on_init` 重建世界。

另一个独立缺陷是 `production_snapshot`：当 `get_entity_by_unit_number` 暂时返回空时，它会把记录删除。炉 32 在 0.8.0 迁移前已经不在持久表中，因此没有被自动恢复，继续保持 unowned legacy machine。

修复：mod `0.8.0`、schema 8 改存可序列化记录，字段包含 `agent_id`、`unit_number`、`entity_name`、`surface`、坐标和 `placed_tick`。schema 7 的布尔项无法复活，但一次性 provenance repair 只恢复同时满足编号、名称、坐标和势力的 27–31。查询不再删除暂时找不到的记录。

验证：

- 新放置的炉 32 在当前会话中写入所有权，保存、重启后仍为 `owned=true`。
- 用户在线时再次保存、重启，炉 32 仍为 `owned=true`；当时客户端脚本尚未更新，所以最后的人类重新加入复核改由 0.8.0 加载后完成。
- 0.8.0 加载后，27–31 均返回 `agent_id=mira` 且 `owned=true`；炉 32 明确保持 `owned=false`。人类角色仍是 unit 1，`game.speed=1`。
- 已移除会误删记录的查询逻辑。未执行 `remove_own_entity` 的破坏性测试，避免拆除现有机器。
